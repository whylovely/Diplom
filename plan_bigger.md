# SaaS Migration Plan: Монолит → API-First архитектура

> **Версия:** 1.0 | **Статус:** Draft for Review  
> **Тип продукта:** Финансовое SaaS-приложение  
> **Методология:** Итеративная (Scrum), 5 фаз, параллельные стримы с Фазы 3

---

## ADR: Выбор клиентского стека

### Контекст

Финансовое SaaS-приложение, монолит на .NET. Команда предположительно имеет существующую экспертизу в C#. Необходимо выбрать между двумя стратегиями построения клиентов.

### Сравнительный анализ

| Критерий | TypeScript / React + Flutter | Blazor WebAssembly + .NET MAUI |
|---|---|---|
| **Time-to-Market** | ✅ Быстрее. Зрелые UI-библиотеки (Shadcn, MUI, TailwindUI) сокращают реализацию финансового UI на 20–30%. Flutter имеет богатую экосистему готовых компонентов. | ⚠️ Медленнее. Blazor WASM требует дополнительной настройки AOT-компиляции; .NET MAUI на iOS/Android имеет более высокий порог входа по сравнению с Flutter. |
| **Рынок труда** | ✅ Широкий. React — крупнейший пул кандидатов на рынке. Flutter растёт, разработчики доступны. | ⚠️ Ограниченный. Blazor WASM — нишевая технология. Senior-специалисты значительно дороже и редки. .NET MAUI относительно молодой продукт. |
| **Порог входа для команды** | ⚠️ Средний. Dart/Flutter требует освоения нового языка. TypeScript — переходный барьер для C#-разработчиков минимален. | ✅ Низкий. C#-команда сразу продуктивна в Blazor. .NET MAUI — продолжение знакомой парадигмы. |
| **Runtime-производительность** | ✅ Высокая. React: V8 JIT, стабильные 60fps. Flutter: Impeller-рендерер обеспечивает нативную производительность анимаций финансовых графиков. | ⚠️ Вариативная. Blazor WASM: начальная загрузка 8–15 МБ (.NET runtime в браузере). Критично для мобильных сетей. |
| **Офлайн-режим (мобайл)** | ✅ Зрелый. Flutter + Hive/SQLite — паттерны offline-first хорошо отработаны в экосистеме. | ⚠️ Решаемый. .NET MAUI + SQLite работает, но документация по offline-sync менее зрелая. |
| **Vendor lock-in** | ✅ Минимальный. Независимость от вендора. React и Flutter открыто управляются сообществом/Google. | ❌ Высокий. Полная зависимость от Microsoft roadmap. История крупных breaking changes в MAUI (Xamarin → MAUI). |
| **Стоимость разработки (TCO 3 года)** | ⚠️ Средняя. React-разработчики дешевле Blazor-специалистов. Два разных языка (TS + Dart) увеличивают накладные расходы на onboarding. | ⚠️ Средняя. C#-монокоманда снижает onboarding-стоимость, но дефицит Blazor-специалистов поднимает ставки. |
| **Экосистема компонентов** | ✅ Богатая. Десятки финансовых chart-библиотек (TradingView Lightweight Charts, Recharts, Nivo). | ⚠️ Достаточная. MudBlazor, Radzen — качественны, но выбор уже. Финансовые графики — нишевые пакеты. |

### Решение

**Рекомендован: TypeScript/React + Flutter** при условии, что команда инвестирует 2–3 спринта в освоение Dart.

**Blazor WASM + .NET MAUI** обоснован только если:
- (а) команда полностью C#-монолитна и найм не планируется
- (б) горизонт продукта ≤ 2 года
- (в) бюджет не допускает найма React/Flutter специалистов

## Фаза 1: Проектирование и архитектура (Sprint 0)

**Цель:** Зафиксировать неизменяемые контракты до начала параллельной разработки.

### Активности

**API Design-First**
- Проектирование RESTful API (или GraphQL) с обязательным contract-testing (Pact или Dredd)
- Swagger/OpenAPI — не просто документация, а исполняемый контракт
- Каждый эндпоинт покрывается consumer-driven contract-тестом до написания имплементации
- Документирование всех эндпоинтов через Swagger/OpenAPI; параллельный старт фронтенда и мобайла через мок-серверы (Prism/WireMock)

**Architecture Decision Records (ADR)**
- Каждое архитектурное решение — файл `docs/adr/NNN-title.md` в системе контроля версий
- Обязательные ADR: выбор СУБД, стратегия авторизации, стек клиентов, стратегия кэширования
- Отсутствие ADR = технический долг с первого дня

**Threat Model**
- STRIDE-анализ финансового домена
- Финансовые данные — высшая категория чувствительности
- Угрозы идентифицируются до написания кода, не после аудита

**Выбор и утверждение стека**
- Пример: `.NET 8 (API) + PostgreSQL + Redis + React/TypeScript (Web) + Flutter (Mobile)`

**Дизайн UI/UX**
- Создание макетов в Figma для веба и мобильных платформ
- Учёт специфики управления финансами: удобный ввод транзакций большим пальцем, читабельные графики
- Обязательный sign-off стейкхолдеров

### Definition of Done

- [ ] OpenAPI-спецификация покрывает 100% запланированных эндпоинтов, валидирована через Spectral
- [ ] Contract-тесты зелёные на мок-сервере
- [ ] ADR задокументированы: выбор СУБД, авторизация, стек клиентов, стратегия кэширования
- [ ] Figma-макеты согласованы стейкхолдерами (sign-off зафиксирован)
- [ ] Threat Model прошёл ревью командой

| Solution Architect / Tech Lead | 1 | 100% | API Design, ADR, Threat Model |
| Backend Senior | 1 | 50% | Ревью контрактов, консультация по домену |

## Фаза 2: Трансформация бэкенда и инфраструктура

**Цель:** Превратить монолит в отказоустойчивое API-ядро с production-grade инфраструктурой.

### Активности

**Миграция SQLite → PostgreSQL**

Требует отдельного sub-плана — это не задача уровня "настроить EF миграции":

1. Параллельная запись в обе СУБД (Strangler Fig pattern) на период перехода
2. Verification suite: построчное сравнение агрегированных отчётов между SQLite и PostgreSQL
3. Zero-downtime cutover: переключение за один транзакционный момент
4. Перенастройка Entity Framework Core, создание новых миграций

> ⚠️ SQLite хранит DECIMAL как REAL — критический риск потери точности финансовых данных. Выделите отдельного разработчика на 1.5–2 недели.

**Внедрение Identity & Security**
- Отказ от простых сессий в пользу OAuth 2.0 / JWT
- **Keycloak** — предпочтительный выбор: self-hosted, GDPR-compliant, богатая документация
- **IdentityServer** — если планируется продажа on-premise версии
- Не использовать кастомную реализацию ни при каких обстоятельствах
- Spike-задача (2 дня): один разработчик реализует e2e авторизацию прежде, чем команда начнёт зависящие задачи

**Оптимизация производительности**
- Внедрение Redis для кэширования курсов валют (`CbrExchangeRateService`): TTL ≤ 30 минут
- Реализация circuit-breaker (Polly) для graceful degradation при недоступности ЦБ API
- Fallback: использовать последний закэшированный курс с отображением предупреждения в UI
- Кэширование часто запрашиваемых агрегированных отчётов

**CI/CD Pipeline**
- Настройка GitHub Actions или GitLab CI
- Каждое слияние в `main` автоматически: запускает тесты → собирает Docker-образы → деплоит на Staging
- SAST-сканирование (Semgrep/SonarQube) настроено и не блокируется critical findings
- Целевое время от коммита до деплоя на staging: ≤ 15 минут

### Definition of Done

- [ ] Все интеграционные тесты проходят на PostgreSQL; нулевое расхождение агрегированных данных при сравнении с SQLite
- [ ] JWT-аутентификация работает end-to-end; refresh-token rotation реализован
- [ ] p99 latency критичных эндпоинтов ≤ 200мс при нагрузке 100 RPS (Locust benchmark)
- [ ] CI/CD pipeline: от коммита до деплоя на staging ≤ 15 минут
- [ ] SAST-сканирование настроено, critical findings — нулевые

### Team Topology

| Роль | Кол-во | Загрузка | Ответственность |
|---|---|---|---|
| Backend Senior | 2 | 100% | Миграция, авторизация, API |
| DevOps / Platform Engineer | 1 | 100% | CI/CD, Docker, Redis |
| QA Engineer | 1 | 50% | Ранний старт интеграционных тестов |
| DBA (консультант) | 1 | 30% | Миграция схемы, индексы |

### Риски Фазы 2

| Риск | Влияние | Вероятность | Митигация |
|---|---|---|---|
| Потеря точности данных при миграции SQLite (REAL) → PostgreSQL (NUMERIC) | **Критическое** | Средняя | Verification suite: допуск ≤ 0.01 коп. Параллельная запись 2 недели. Cutover только после нулевого расхождения в 3 последовательных run. |
| Задержки внедрения OAuth 2.0 / смена парадигмы авторизации | Высокое | Средняя | Spike-задача (2 дня) до старта зависимых модулей. Не начинать зависимые задачи без зелёного spike. |
| Деградация CbrExchangeRateService при недоступности ЦБ API | Среднее | Средняя | Circuit-breaker (Polly) + Redis TTL 30 мин. Fallback на последний закэшированный курс. Алерт при Redis-недоступности. |

## Фаза 3: Разработка клиентов (параллельные стримы)

**Цель:** Реализовать Web и Mobile клиенты параллельно, опираясь на зафиксированные контракты.

> ⚠️ **Параллелизм — условный, не безусловный.** Стримы расходятся только при наличии стабильного мок-сервера и Pact Broker. Без этой инфраструктуры параллельная разработка превращается в параллельное накопление технического долга.

### Web Frontend (React + TypeScript)

- Генерация TypeScript-клиентов через `openapi-generator-cli` в CI — клиент никогда не пишется вручную
- Feature-флаги (LaunchDarkly или self-hosted) для инкрементального rollout финансовых модулей
- **Performance budget:** First Contentful Paint ≤ 1.5с, Largest Contentful Paint ≤ 2.5с на 4G-соединении
- Финансовые графики: TradingView Lightweight Charts для свечных/линейных; Recharts для агрегированных отчётов из `ReportController`
- Разработка компонентов: Дашборд, Журнал транзакций, Настройки категорий

### Mobile App (Flutter)

**Offline-first архитектура:**
- Локальный SQLite (drift/isar) + background sync через WorkManager
- Конфликты разрешаются server-wins с уведомлением пользователя
- Каждая транзакция имеет client-generated UUID + created_at timestamp

**Безопасность:**
- Биометрия: `local_auth` package; токены — исключительно в Secure Enclave/Android Keystore, никогда в SharedPreferences
- Интеграция FaceID/TouchID для быстрого входа

**Push-уведомления:**
- Firebase Cloud Messaging
- Напоминания о регулярных платежах за 3 и 1 день до дедлайна

### Definition of Done

- [ ] Web: Lighthouse score ≥ 85 (Performance, Accessibility, Best Practices)
- [ ] Mobile: crash-free rate ≥ 99.5% на TestFlight/Firebase App Distribution beta (≥ 50 тестировщиков)
- [ ] Все ключевые user stories покрыты E2E-тестами (Playwright для web, Patrol для Flutter)
- [ ] Оффлайн-сценарий: транзакция без сети синхронизируется корректно после восстановления соединения

## Фаза 4: QA и стабилизация

**Цель:** Валидация системы под нагрузкой, устранение уязвимостей, подготовка к production.

### Активности

**Интеграционное тестирование**
- Проверка связок: Mobile → API → База и Web → API → База
- Регрессионный набор: ≥ 200 E2E-сценариев, pass rate 100%

**Нагрузочное тестирование (k6 / JMeter)**

Целевые метрики:

| Метрика | Цель |
|---|---|
| Concurrent users | 1 000 |
| p95 latency | ≤ 500мс |
| Error rate | ≤ 0.1% |

Сценарий нагрузки учитывает пиковое использование финансового приложения: утро понедельника, конец месяца — пиковое создание транзакций.

Предварительно: включить EF Core query logging в staging, отловить N+1 запросы через MiniProfiler до нагрузочного теста.

**Security Audit — OWASP API Security Top 10**

Обязательные проверки:
- **BOLA** (Broken Object Level Authorization): тест на доступ к `/api/accounts/{id}` чужого пользователя — должен возвращать 403, не данные
- **Mass assignment**: все входные DTO используют `[JsonIgnore]` / whitelist-маппинг
- Использование UUID вместо sequential integer ID для публичных эндпоинтов
- Пентест: минимум один день автоматизированного сканирования через OWASP ZAP + ручная верификация

**Chaos Engineering (рекомендуется)**

Один chaos-эксперимент: отключить Redis и убедиться, что система деградирует gracefully — не падает, возвращает актуальные данные напрямую из БД с увеличенной латентностью.

### Definition of Done

- [ ] Нагрузочный тест: все целевые метрики выполнены
- [ ] Zero critical/high уязвимостей по итогам пентеста
- [ ] Регрессионный набор: ≥ 200 E2E-сценариев, pass rate 100%
- [ ] MTTR (Mean Time To Recover) для staging-инцидентов задокументирован

### Team Topology

| Роль | Кол-во | Загрузка |
|---|---|---|
| QA Lead | 1 | 100% |
| QA Engineer | 2 | 100% |
| Security Engineer (внешний) | 1 | 30% |
| DevOps | 1 | 100% — нагрузочные стенды |
| Backend Developer | 1 | 50% — исправление дефектов |

### Риски Фазы 4

| Риск | Влияние | Вероятность | Митигация |
|---|---|---|---|
| BOLA-уязвимость: пользователь A получает данные пользователя B | **Критическое** | Средняя | Обязательная проверка владельца ресурса на уровне сервисного слоя (не только контроллера). OWASP ZAP + ручной пентест. UUID вместо integer ID. |

## Фаза 5: Развёртывание и запуск

**Цель:** Безопасный выход в production с возможностью мгновенного rollback.

### Production Architecture

**База данных:**
- PostgreSQL кластер: Primary + 2 Read Replicas (Patroni для автоматического failover)
- Backup: ежедневный full + WAL-archiving (Point-in-Time Recovery с RPO ≤ 1 час)

**Application layer:**
- Nginx как L7 load balancer + SSL termination
- Upstream — минимум 2 инстанса .NET API за балансировщиком
- Docker + Kubernetes (k3s для старта при ограниченном бюджете; managed cluster EKS/GKE при масштабировании)

### Стратегии безопасного развёртывания

**Blue-Green Deployment — рекомендован для финансового SaaS:**

1. Полная копия production-среды (Green) разворачивается параллельно Blue
2. После smoke-тестов трафик переключается на уровне load balancer (один DNS/IP change)
3. Blue остаётся "горячим" 30 минут — мгновенный rollback при обнаружении регрессий
4. Обе среды подключены к одному Primary PostgreSQL — только application layer отличается

> Требование: удвоенная инфраструктурная стоимость на период переключения (~1 час). Rollback = переключение LB обратно на Blue, данные не затронуты.

**Canary Deployment — применять для feature-релизов после стабилизации:**

1. 5% трафика → новая версия, мониторинг 30 минут
2. 25% трафика → мониторинг 30 минут
3. 100% трафика

Canary routing через Nginx `split_clients` или Istio weight-based routing. Автоматический rollback если error rate Canary превышает Baseline + 0.5%.

### Мониторинг и алертинг

**Стек:** Prometheus (метрики) + Grafana (дашборды) + Loki (логи)

> ELK — только если команда уже имеет экспертизу. PLG-стек дешевле в эксплуатации.

**Обязательные алерты (PagerDuty / Alertmanager):**
- p95 latency > 1с на протяжении 5 минут
- Error rate > 1%
- PostgreSQL replication lag > 30с
- Диск > 80%

### SLO (Service Level Objectives)

| Индикатор | SLO Target | Окно измерения |
|---|---|---|
| Availability | 99.5% | Rolling 30 дней |
| API p95 latency | ≤ 500мс | Rolling 24 часа |
| Error rate | ≤ 0.1% | Rolling 24 часа |
| RTO (Recovery Time Objective) | ≤ 1 час | Per incident |
| RPO (Recovery Point Objective) | ≤ 1 час | Per incident |

### Публикация мобильных приложений

> ⚠️ **App Store Review — на критическом пути.** Финансовые приложения проходят расширенную проверку. Первая тестовая сборка должна уйти на ревью в начале **Фазы 4**, не Фазы 5. Закладывайте 10–14 рабочих дней как буфер по умолчанию.

- Privacy Policy и Terms of Service подготовлены до сабмита
- Финансовые приложения требуют дополнительной документации от Apple/Google — подготовить заранее
- TestFlight (iOS) и Internal Testing (Google Play) запускаются в начале Фазы 4

### Definition of Done

- [ ] Blue-Green cutover выполнен без ошибок на staging, runbook задокументирован
- [ ] Rollback-процедура протестирована (не просто задокументирована)
- [ ] SLO-дашборд зелёный на протяжении 72 часов после запуска
- [ ] Мобильные приложения прошли App Store Review и Google Play Review

|---|---|---|
| DevOps / Platform Engineer | 1–2 | 100% |
| Backend Senior | 1 | 50% — hotfix-дежурство |
| QA Engineer | 1 | 100% — smoke-тесты, мониторинг |
| Tech Lead | 1 | 50% — управление инцидентами |

### Риски Фазы 5

## Финальные рекомендации

### Три критических момента, которые план недооценивает

**1. Параллелизм Фазы 3 — условный, не безусловный**

Стримы расходятся только при наличии стабильного мок-сервера и Pact Broker. Без этой инфраструктуры «параллельная разработка» превращается в параллельное накопление технического долга, который взрывается при первой интеграционной сессии.

**2. Финансовая миграция данных — отдельный проект внутри Фазы 2**

Это не задача уровня "настроить EF миграции". Потребуется написание, тестирование и верификация migration pipeline. Выделите отдельного разработчика на 1.5–2 недели с явным milestone: нулевое расхождение агрегатов.

**3. App Store Review — на критическом пути**

Финансовые приложения проходят расширенную проверку, особенно в App Store. Первая сборка должна уйти на ревью в начале Фазы 4, не в Фазе 5. Закладывайте 10–14 рабочих дней в план как буфер по умолчанию.
